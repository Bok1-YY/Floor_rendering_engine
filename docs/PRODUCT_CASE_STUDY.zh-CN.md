# Floor Rendering Engine：AI 产品案例

[返回 README](../README.md) · [English](./PRODUCT_CASE_STUDY.en.md)

## 一句话概述

Floor Rendering Engine 是面向地板行业社媒团队的 AI 视觉生产系统。它不是把一个生图 API 包进网页，而是把色板理解、空间策划、批量生成、颜色校准、局部修补、评审和交付串成可运行的生产闭环。

> 项目状态：已在真实公司社媒流程中使用；核心产品设计与工程实现由我独立完成。公司、客户与商业数据均做了脱敏或区间化表达。

## 1. 背景与用户

主要用户是约 10 人的公司社媒团队。他们需要持续为地板产品生产 Pinterest 等渠道使用的室内场景图。

原流程表面上是“生成五张图”，实际包含了更多隐性工作：

1. 理解一块平面地板色板适合什么空间；
2. 想象房间结构、家具、光线与铺装方式；
3. 编写和反复调整提示词；
4. 多轮调用模型，从约 10 张结果中选出 1 张；
5. 修正产品偏色、局部穿帮和构图问题；
6. 下载、命名、评审和交付。

整套过程约 1 小时只能完成 5 张图。瓶颈并不只是模型生成速度，而是围绕模型的大量认知劳动和返工。

## 2. 问题定义

我把最初的“做一个地板效果图生成器”拆成四个产品目标：

| 目标 | 需要回答的问题 |
|---|---|
| 降低创作门槛 | 不擅长提示词和空间想象的人能否稳定产出？ |
| 提高可用率 | 能否减少“生成很多、真正能用的很少”？ |
| 保证产品真实性 | 地板颜色、板型、铺法和光泽能否尽量接近真实商品？ |
| 建立生产闭环 | 生成之后能否继续修补、评审、追踪成本并交付？ |

因此，核心北极星不是“每天调用多少次模型”，而是**单位时间内得到的可交付图片数**。

## 3. 产品策略

### 3.1 把行业知识做成参数，而不是要求每个人写长提示词

用户从色板开始，选择房间、铺法、板宽、倒角、缝隙、光泽与人物/宠物等业务参数。系统把这些结构化选择编译为模型提示词，并可用 AI 场景代笔补全构图和叙事。

这一步把提示词工程从个人技巧转成团队可复用的产品能力。

### 3.2 用多模型和批量候选处理不确定性

同一任务可并行走 B2、Pro 或实验性 SD 线路。不同模型使用独立并发槽，失败可重试或切线，任务和请求句柄持久化。用户不必守着一次调用，而是直接得到一组带来源的候选。

### 3.3 把品牌色一致性设计进工作流

仅靠提示词无法稳定保留地板颜色。系统用 MobileSAM 找出地板区域，再在 LAB 色彩空间内向色板目标校正；校色被限制在蒙版内，避免同时改变墙面、家具和环境光。

![自动校色前后对比](./media/quality-before-after.webp)

### 3.4 用“AI 初稿 + 人工控制”处理局部修补

生成式添加和移除同时提供 AI 智能选区与传统画笔。自动扫描适合快速选中家具，单点分割适合指定地面、墙面或桌面；画笔和橡皮用于补阴影、遮挡和细边。

这个设计不假设模型永远正确，也不让失败把用户堵死。

![智能选区交互](./media/smart-mask.gif)

### 3.5 让生成结果进入运营闭环

系统保留任务、模型、原图、自动校色版本和人工处理版本的关系，并提供通过、备选、淘汰、最佳、问题标签、用量估算和 HTML/PPTX 导出。

## 4. 关键迭代

| 阶段 | 用户问题 | 产品变化 |
|---|---|---|
| 原型 | 每次都要重新构思和写提示词 | 结构化行业参数 + 场景模板 |
| 批量生产 | 单次调用慢、失败后要手工重来 | 多模型并发、候选批量生成、队列与重试 |
| 质量控制 | 地板颜色漂亮但不代表真实商品 | MobileSAM 地板蒙版 + LAB 自动校色 |
| 局部修改 | 穿帮物件只能慢慢涂画笔 | 通用物件扫描、点击分割、生成式添加/移除 |
| 真实反馈 | 用户点击智能选区后“没反应” | 即时状态反馈、单点请求优先、扫描锁分段释放 |
| 团队运营 | 图片散落，难复盘成本与好图模式 | 记录、评审、标签、用量与提案导出 |

### “点击没反应”如何改变实现

智能选区初版通过了模型和路由测试，但真实浏览器中点击未命中候选时会静默返回；完整扫描又长期占用推理锁，使单点识别只能排队。

我在隔离端口复现后做了三项调整：

1. 未命中点击立即显示“正在识别”，不再静默；
2. 自动扫描在每个网格点之间释放共享锁，让显式点击优先；
3. 单点结果与随后完成的后台候选合并，不覆盖用户已经选择的区域。

这次迭代提醒我：AI 功能的产品质量不仅是模型精度，也包括等待是否可理解、失败是否可恢复、用户意图是否被优先执行。

## 5. 结果与口径

| 结果 | 当前观测 | 口径 |
|---|---|---|
| 真实用户 | 约 10 人 | 公司社媒组实际使用人数 |
| 效率 | 原约 1 小时 / 5 张；现可直接批量出图 | 原时间包含构思、提示词和生成后处理；当前下限主要由 API 速度决定 |
| 可用率 | 普通图多数首轮可用；特殊图平均约 2 张内可用 | 与原约 10 张选 1 张的日常经验对比 |
| 成本 | 约降低 80% | 团队内部估算，含 API 重试与人工时间 |
| 规模 | 近 2,000 张 | 系统累计生成量 |
| 渠道指标 | Pinterest 点赞用户到下单月度约 4% | 团队内部月度统计；为运营综合结果，不做单一产品因果归因 |

这些数据不是严谨的随机对照实验。当前证据适合说明工作流发生了显著改善，但不足以单独证明系统导致了全部销售结果。

## 7. 局限与下一步

- **指标基础设施**：把当前人工统计升级为匿名事件埋点，明确首轮通过率、单张人工时长、模型重试率和渠道素材 ID。
- **实验设计**：对不同场景模板、模型路线和校色强度做分层对照，避免只看总体平均值。
- **团队化部署**：目前默认本机单用户运行；多人 SaaS 需要身份认证、租户隔离、对象存储、队列服务和审计。
- **分割边界**：透明、反射、细长或严重遮挡物仍可能需要画笔；后续可加入语义标签和用户修正反馈闭环。
- **业务归因**：把导出的素材与 Pinterest 发布和订单链路关联，才能更可信地分析内容对转化的增量影响。
